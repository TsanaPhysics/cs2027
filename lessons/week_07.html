ผลลัพธ์การเรียนรู้ระดับสัปดาห์ (Weekly Learning Outcomes: WLOs)

เมื่อสิ้นสุดการจัดกิจกรรมการเรียนรู้สัปดาห์ที่ 7 นักศึกษาครูวิทยาศาสตร์สามารถแสดงสมรรถนะ 4 มิติเชิงบูรณาการในการทดสอบและตรวจหาข้อผิดพลาดของแบบจำลองวิทยาศาสตร์ได้ดังนี้:

WLO 1: ความรู้ด้านอนุกรมวิธานข้อผิดพลาด (Error Taxonomy)

สามารถจำแนก เปรียบเทียบ และอธิบายกลไกการเกิดข้อผิดพลาด 3 ประเภทในโปรแกรมวิทยาศาสตร์ ได้แก่ Syntax Error (ข้อผิดพลาดทางไวยากรณ์), Runtime Error / Exceptions (ข้อผิดพลาดขณะรันโปรแกรม เช่น ZeroDivisionError, IndexError, ValueError), และ Logic Error (ข้อผิดพลาดเชิงตรรกะและสูตรทางวิทยาศาสตร์) ได้อย่างแม่นยำ

WLO 2: วงจรการดีบักและชุดกรณีทดสอบ (Scientific Debugging & Test Cases)

สามารถประยุกต์ใช้วงจรการดีบักเชิงวิทยาศาสตร์ (Scientific Debugging Cycle: Hypothesize $\rightarrow$ Instrument $\rightarrow$ Observe $\rightarrow$ Refine) และออกแบบชุดกรณีทดสอบแบบครอบคลุม (Test Cases: Normal, Edge/Boundary, Invalid Cases) เพื่อตรวจสอบความเที่ยงตรงของแบบจำลองการทดลองเสมือนจริงได้อย่างเป็นระบบ

WLO 3: การเขียนโปรแกรมป้องกันข้อผิดพลาด (Defensive Programming)

พัฒนาโปรแกรม Scratch และ Python 3.11 โดยใช้กลไกการเขียนโปรแกรมเชิงป้องกัน (Defensive Guard) ด้วยคำสั่ง try...except, assert, Type Hints และการตรวจจับขอบเขตของตัวแปรก่อนคำนวณ เพื่อให้แบบจำลองทางวิทยาศาสตร์มีความเสถียร ไม่ขัดข้อง (Crash) เมื่อเผชิญกับข้อมูลนำเข้าที่ผิดปกติ

WLO 4: การสอนเชิงสร้างสรรค์และการส่งเสริม Growth Mindset (Pedagogy & Mindset)

สามารถออกแบบแผนการจัดการเรียนรู้วิทยาศาสตร์ที่เปลี่ยน "ความผิดพลาด (Bugs)" ให้กลายเป็น "โอกาสในการเรียนรู้ (Productive Failure / Growth Mindset)" พร้อมทั้งฝึกทักษะการตรวจสอบความสมเหตุสมผลของผลลัพธ์ทางวิทยาศาสตร์แก่นักเรียนตามแนวคิดระเบียบวิธีทางวิทยาศาสตร์

การเชื่อมโยงผลลัพธ์การเรียนรู้ระดับหลักสูตร (CLO Alignment): สอดรับกับ CLO2: สามารถออกแบบและเขียนโปรแกรมคอมพิวเตอร์อย่างง่ายเพื่อจำลองแบบทางวิทยาศาสตร์ และ CLO3: ตระหนักถึงความสำคัญ จริยธรรม และความรับผิดชอบในการใช้เทคโนโลยีคำนวณเพื่อการสอน โดยเฉพาะการส่งมอบแบบจำลองที่มีความถูกต้องทางวิชาการและปลอดภัยต่อการเรียนรู้

สาระสำคัญเชิงวิชาการ & สื่อทัศนศิลป์ (No Text-Wall Visual Architecture)

ในวงการวิทยาการคำนวณ การตรวจหาและแก้ไขข้อผิดพลาด (Debugging) มิใช่เพียงการแก้โค้ดให้รันผ่าน แต่เป็นกระบวนการสืบเสาะทางวิทยาศาสตร์ (Scientific Inquiry) เพื่อยืนยันว่า "แบบจำลองคอมพิวเตอร์สามารถสะท้อนความจริงทางธรรมชาติได้อย่างถูกต้องและเที่ยงตรง"

ข้อผิดพลาดในโปรแกรมจำลองวิทยาศาสตร์จำแนกออกเป็น 3 ระดับ ซึ่งมีระดับความร้ายแรงและเทคนิคในการตรวจหาที่แตกต่างกันอย่างสิ้นเชิง:

ภาพผังที่ 7.1: อนุกรมวิธานข้อผิดพลาดในโปรแกรมจำลองวิทยาศาสตร์ (Taxonomy of Scientific Programming Errors)
แสดงการเปรียบเทียบสเปกตรัมข้อผิดพลาด 3 ประเภทในโปรแกรมวิทยาศาสตร์ โดย Logic Error เป็นข้อผิดพลาดที่ร้ายแรงและตรวจพบได้ยากที่สุด

2. วงจรการดีบักเชิงวิทยาศาสตร์ (Scientific Debugging Cycle: Hypothesize-Test Workflow)

การดีบักที่ทรงประสิทธิภาพมิใช่การ "สุ่มแก้โค้ดไปเรื่อยๆ (Trial and Error)" แต่นักศึกษาครูวิทยาศาสตร์ต้องใช้ วงจรการดีบักเชิงวิทยาศาสตร์ ซึ่งมีกระบวนการเหมือนกับ ระเบียบวิธีทางวิทยาศาสตร์ (Scientific Method) ทุกประการ โดยเปลี่ยนจากการศึกษาสิ่งแวดล้อมธรรมชาติมาเป็นการศึกษาพฤติกรรมของซอฟต์แวร์

ภาพผังที่ 7.2: วงจรการดีบักเชิงวิทยาศาสตร์เปรียบเทียบกับระเบียบวิธีทางวิทยาศาสตร์ (Scientific Debugging Cycle)
print(f"DEBUG: v={v}") หรือ Breakpoint ✓ ตรวจสอบสถานะของตัวแปรก่อนและหลังคำนวณสูตร ขั้นที่ 4: แก้ไขโค้ดและทดสอบซ้ำ (Refine & Validate) • ระเบียบวิธีวิทย์: สรุปผลและเผยแพร่ทฤษฎีที่ตรวจสอบแล้ว • การดีบักโค้ด: แก้ไขสูตร ใส่ Defensive Guard ดักจับ Error ✓ Regression Test: รันชุดทดสอบเดิมทั้งหมดเพื่อยืนยันว่าไม่กระทบส่วนอื่น
แสดงขั้นตอนวงจรการดีบักเชิงวิทยาศาสตร์ 4 ขั้นตอนที่เทียบเคียงกับระเบียบวิธีทางวิทยาศาสตร์อย่างเป็นรูปธรรม

3. การออกแบบชุดกรณีทดสอบและการตรวจสอบความถูกต้องของแบบจำลอง (Test Cases & Model Validation Pipeline)

ภาพผังที่ 7.3: ท่อทดสอบและยืนยันความถูกต้องของแบบจำลองวิทยาศาสตร์ (Model Verification & Validation Pipeline)
แสดงกระบวนการทดสอบยืนยันความถูกต้องของแบบจำลอง (Verification & Validation: V&V) ผ่านชุดกรณีทดสอบ 3 มิติ

ตารางที่ 7.1: เมทริกซ์วิเคราะห์ข้อผิดพลาดในโปรแกรมวิทยาศาสตร์ สาเหตุ และแนวทางป้องกันเชิงรุก

ประเภทข้อผิดพลาด ตัวอย่างในวิชาฟิสิกส์/เคมี/ชีวะ สาเหตุเชิงคอมพิวเตอร์ แนวทางป้องกันและดีบักเชิงรุก
Syntax Error พิมพ์สูตรแก๊สอุดมคติผิด:
P * V = n * R * T
(ใช้ = กำหนดค่าในฝั่งซ้ายของตัวแปรคณิตศาสตร์) 		ตัวแปลภาษา (Parser) ไม่สามารถแปลงโค้ดเป็น Abstract Syntax Tree ได้ เนื่องจากละเมิดกฎไวยากรณ์ภาษา ใช้ IDE ที่มีระบบ Linter / Syntax Highlighting (เช่น Thonny, VS Code) ช่วยตรวจจับแบบเรียลไทม์
Runtime Error คำนวณความดันในกระบอกสูบตามกฎของบอยล์ ($P_2 = \frac{P_1V_1}{V_2}$) เมื่อผู้ใช้ป้อนปริมาตร $V_2 = 0$ เกิด ZeroDivisionError หรือ IndexError เมื่อพยายามดึงข้อมูลเกินดัชนีของอาร์เรย์ ครอบด้วยโครงสร้าง try...except และเขียนเงื่อนไขตรวจสอบ (Pre-condition Guard) ก่อนคำนวณ
Logic Error คำนวณระยะทางตกอิสระ $s = ut + \frac{1}{2}gt^2$ แต่เขียนโค้ดเป็น s = u * t + 1/2 * g * t (ลืมยกกำลังสอง) ลำดับความสำคัญของเครื่องหมาย (Operator Precedence) ผิด หรือแปลความหมายของสมการคณิตศาสตร์คลาดเคลื่อน ใส่การพิมพ์ค่าตัวแปร (Print Debugging), เทคนิค Rubber Duck, และเขียน Unit Testing ด้วยคำสั่ง assert

โค้ดตัวแบบจำลอง Python 3.11: ระบบแบบจำลองฟิสิกส์พร้อมกลไกดีบักและการทดสอบอัตโนมัติ (Automated Testing)

ตัวอย่างโค้ดโปรแกรมคำนวณพลังงานกลและจำลองการเคลื่อนที่แนวราบ พร้อมระบบ Defensive Guard และ Test Suite ตรวจสอบความถูกต้องทางฟิสิกส์: 

# ==============================================================================
# โปรแกรม: Physics Simulation Engine with Automated Verification & Debugging
# รายวิชา: 4124941 วิทยาการคำนวณสำหรับการสอนวิทยาศาสตร์ | ผศ.ดร.ชีวะ ทัศนา
# ==============================================================================
from typing import Dict, Union

def calculate_kinetic_energy(mass: float, velocity: float) -> float:
    """
    คำนวณพลังงานจลน์ (Kinetic Energy: Ek = 0.5 * m * v^2)
    พร้อมกลไก Defensive Programming ตรวจจับข้อผิดพลาดทางฟิสิกส์
    """
    # 1. Defensive Guard: มวลต้องเป็นจำนวนจริงบวก
    if mass < 0:
        raise ValueError(f"ข้อผิดพลาดทางฟิสิกส์: มวลไม่สามารถติดลบได้ (mass={mass} kg)")
    
    # 2. Defensive Guard: อัตราเร็วต้องไม่เกินความเร็วแสง (c = 3x10^8 m/s)
    SPEED_OF_LIGHT = 3.0e8
    if abs(velocity) > SPEED_OF_LIGHT:
        raise ValueError(f"ข้อผิดพลาดทางฟิสิกส์: ความเร็วต้องไม่เกินความเร็วแสง (v={velocity} m/s)")
        
    # 3. คำนวณตามกฎทางฟิสิกส์ (ระวัง Operator Precedence)
    ek = 0.5 * mass * (velocity ** 2)
    return round(ek, 4)

def run_simulation_tests():
    """
    ฟังก์ชัน Automated Test Suite ตรวจสอบแบบจำลองทางฟิสิกส์
    ครอบคลุม Normal Cases, Boundary Cases และ Error Handling
    """
    print("=" * 60)
    print("🚀 เริ่มต้นการทดสอบแบบจำลองทางวิทยาศาสตร์ (Running Automated Tests)")
    print("=" * 60)
    
    # กรณีทดสอบที่ 1: Normal Case (ค่าปกติ)
    # วัตถุมวล 2 kg เคลื่อนที่ด้วยความเร็ว 3 m/s -> Ek = 0.5 * 2 * 9 = 9.0 J
    test1 = calculate_kinetic_energy(2.0, 3.0)
    assert test1 == 9.0, f"Test 1 ล้มเหลว! ได้ค่า {test1} แทนที่จะเป็น 9.0"
    print("✓ Test 1 Passed: ค่าปกติ (Normal Case: m=2, v=3 -> Ek=9.0 J)")
    
    # กรณีทดสอบที่ 2: Boundary Case (ขอบเขตวัตถุหยุดนิ่ง)
    # วัตถุหยุดนิ่ง v = 0 -> Ek ต้องเป็น 0 เสมอ
    test2 = calculate_kinetic_energy(50.0, 0.0)
    assert test2 == 0.0, f"Test 2 ล้มเหลว! วัตถุหยุดนิ่งแต่ได้ค่า {test2}"
    print("✓ Test 2 Passed: ขอบเขตวัตถุนิ่ง (Boundary Case: v=0 -> Ek=0.0 J)")
    
    # กรณีทดสอบที่ 3: Defensive Case (ตรวจจับมวลติดลบ)
    try:
        calculate_kinetic_energy(-10.0, 5.0)
        print("❌ Test 3 Failed: โปรแกรมไม่ดักจับมวลติดลบ!")
    except ValueError as e:
        print(f"✓ Test 3 Passed: ตรวจจับข้อผิดพลาดมวลติดลบสำเร็จ ({e})")
        
    # กรณีทดสอบที่ 4: Boundary Case (ความเร็วติดลบ: ถอยหลัง พลังงานจลน์ต้องเป็นบวก)
    test4 = calculate_kinetic_energy(4.0, -5.0)
    assert test4 == 50.0, f"Test 4 ล้มเหลว! ได้ค่า {test4} แทนที่จะเป็น 50.0"
    print("✓ Test 4 Passed: ความเร็วทิศลบ (Negative Velocity: v=-5 -> Ek=50.0 J)")
    
    print("-" * 60)
    print("🎉 ผลการตรวจประเมิน: แบบจำลองผ่านการทดสอบ 100% พร้อมใช้งานในชั้นเรียน")

if __name__ == "__main__":
    run_simulation_tests()

  • อัตราการเพิ่มขึ้นของเวลาประมวลผลสอดคล้องกับความซับซ้อน Big-O ระดับใด?
  • เสนอแนะแนวทางการปรับปรุงขั้นตอนวิธีเพื่อลดการใช้หน่วยความจำลงอย่างน้อย 30%

แผนการจัดกิจกรรมการเรียนรู้เชิงรุก (Active Learning: 5E Instructional Model)

บูรณาการกระบวนการสืบเสาะหาความรู้ 5 ขั้น (5E) ควบคู่กับปฏิบัติการคลินิกผ่าตัดโค้ด (Science Code Doctor Workshop) รวมเวลา 4 ชั่วโมง (240 นาที):

ภาคบรรยาย: อนุกรมวิธานข้อผิดพลาดและจิตวิทยาการดีบักเชิงบวก ชั่วโมงที่ 1 - 2 (120 นาที)

  • ขั้นที่ 1: การสร้างความสนใจ (Engagement - 25 นาที): "โศกนาฏกรรมทางวิทยาศาสตร์จากบั๊กบรรทัดเดียว"
    • ผู้สอนเปิดคลิปวิดีโอประวัติศาสตร์เหตุการณ์ ยานสำรวจดาวอังคาร Mars Climate Orbiter มูลค่ากว่า 327 ล้านดอลลาร์สหรัฐพุ่งชนดาวอังคารสูญสลายไปในปี 1999 เนื่องจากความผิดพลาดในการแปลงหน่วยปอนด์-วินาที เป็นนิวตัน-วินาที ในซอฟต์แวร์
    • เปิดประเด็นคำถาม: "เหตุใดโปรแกรมของ NASA ที่เขียนโดยวิศวกรชั้นนำจึงเกิดข้อผิดพลาดรุนแรงได้? และเราจะสร้างวัฒนธรรมการตรวจสอบแบบจำลองในชั้นเรียนวิทยาศาสตร์อย่างไร?"
    • ชี้ให้เห็นว่าบั๊กเป็นเรื่องธรรมดา และความสามารถในการค้นหาบั๊ก (Debugging Literacy) คือทักษะสำคัญสูงสุดของนักวิทยาการคำนวณ
  • ขั้นที่ 2: การสำรวจและค้นหา (Exploration - 45 นาที): "Live Bug Spotting & Rubber Duck Method"
    • แจกโค้ด Scratch และ Python สั้นๆ 3 ตัวอย่างที่มีบั๊กแฝง (Syntax 1 ข้อ, Runtime 1 ข้อ, Logic 1 ข้อ)
    • ให้นักศึกษาจับคู่และแจก "เป็ดยางดีบัก (Rubber Duck)" ประจำโต๊ะ ให้นักศึกษาผลัดกันอธิบายการทำงานของโค้ดทีละบรรทัดให้เป็ดยางและเพื่อนฟัง
    • สังเกตจุดที่เสียงเริ่มติดขัด เพื่อชี้พิกัดของข้อผิดพลาดเชิงตรรกะในแบบจำลอง
  • ขั้นที่ 3: การอธิบายและลงข้อสรุป (Explanation - 50 นาที): "สถาปัตยกรรมการทดสอบ V&V และการเขียนโค้ดป้องกัน"
    • ผู้สอนสรุปหลักการ Verification (แบบจำลองถูกสร้างขึ้นตามสมการคณิตศาสตร์หรือไม่) เทียบกับ Validation (แบบจำลองสอดคล้องกับพฤติกรรมจริงในธรรมชาติหรือไม่)
    • สอนเทคนิคการใช้คำสั่ง assert เพื่อตรวจสอบผลลัพธ์อัตโนมัติ และการใช้บล็อก try...except Exception as e: ในการดักจับ Runtime Errors
    • สรุปแผนผังวงจรการดีบักเชิงวิทยาศาสตร์ 4 ขั้นตอนร่วมกับผู้เรียน

ภาคปฏิบัติ: ปฏิบัติการคลินิกผ่าตัดโค้ดวิทยาศาสตร์ (Science Code Doctor Workshop) ชั่วโมงที่ 3 - 4 (120 นาที)

  • ขั้นที่ 4: การขยายความรู้ (Elaboration / Workshop - 80 นาที): "Science Code Doctor Challenge"
    • แบ่งนักศึกษาออกเป็นทีมละ 3-4 คน รับบทเป็น "แพทย์ผู้เชี่ยวชาญการตรวจรักษาโค้ด"
    • แจกแฟ้มประวัติคนไข้ 4 เคส (Buggy Simulation Projects):
      • เคสที่ 1 (คนไข้ฟิสิกส์): โปรแกรมจำลองการเคลื่อนที่วิถีโค้ง (Projectile Motion) ที่ลูกบอลตกลงใต้พื้นดินไม่หยุด เนื่องจากขาดเงื่อนไข Floor Collision
      • เคสที่ 2 (คนไข้เคมี): แบบจำลองการเจือจางกรด-เบส ที่คำนวณค่า pH ได้ -1.5 เนื่องจากไม่ได้จำกัดขอบเขตของลอการิทึม
      • เคสที่ 3 (คนไข้ชีววิทยา): แบบจำลองสายใยอาหาร (Food Web) ที่ประชากรสัตว์กินพืชกลายเป็นอนันต์ใน 3 วินาที เพราะลืมใส่ตัวแปรความจุสิ่งแวดล้อม
      • เคสที่ 4 (คนไข้ดาราศาสตร์): แบบจำลองกฎแรงโน้มถ่วงสากลของนิวตัน ($F = G\frac{m_1m_2}{r^2}$) ที่ Crash ทันทีเมื่อดาวเคราะห์สองดวงชนกัน ($r=0$)
    • ทุกกลุ่มต้องเขียน ใบสั่งยาและบันทึกการรักษา (Medical Chart) ระบุ: ชนิดของบั๊ก, บรรทัดที่เกิด, โค้ดที่แก้ไขแล้ว, และชุด Test Case พิสูจน์ความหายขาด
  • ขั้นที่ 5: การประเมินผลและการสะท้อนคิด (Evaluation & Reflection - 40 นาที): "Growth Mindset Showcase & Midterm Readiness"
    • ตัวแทนกลุ่มนำเสนอเคสที่ตนเองรักษาสำเร็จ และแบ่งปันจุดที่เพื่อนในห้องอาจมองข้าม
    • อาจารย์บรรยายสรุปกระตุ้น Growth Mindset: "ไม่มีโปรแกรมเมอร์คนใดในโลกที่เขียนโค้ดครั้งแรกแล้วไม่มีบั๊ก บั๊กไม่ใช่ความล้มเหลว แต่เป็นสารตั้งต้นของความเข้าใจอย่างลึกซึ้ง"
    • ชี้แจง Checklist ทบทวนความรู้สำหรับ การสอบกลางภาคในสัปดาห์ที่ 8

เกณฑ์การวัดและประเมินผลตามสภาพจริง (Authentic Assessment Rubrics)

เกณฑ์รูบริกส์จำแนก 4 ระดับคุณภาพ สอดคล้องกับมาตรฐาน WLOs ทั้ง 4 มิติ สำหรับการประเมินทักษะการดีบักและการสร้างแบบจำลองวิทยาศาสตร์:

เกณฑ์การประเมิน ดีมาก (4 คะแนน) ดี (3 คะแนน) พอใช้ (2 คะแนน) ปรับปรุง (1 คะแนน)
1. การจำแนกและระบุสาเหตุข้อผิดพลาด (Error Diagnostics) สามารถจำแนกระหว่าง Syntax, Runtime และ Logic Error ได้อย่างแม่นยำ 100% อธิบายกลไกที่คอมไพเลอร์ขัดข้องได้อย่างชัดเจน จำแนกประเภทข้อผิดพลาดได้ถูกต้องส่วนใหญ่ อธิบายสาเหตุของบั๊กในบริบทวิทยาศาสตร์ได้ จำแนกประเภทข้อผิดพลาดได้บางส่วน แต่ยังสับสนระหว่าง Runtime Error และ Logic Error ไม่สามารถระบุได้ว่าข้อผิดพลาดที่เกิดขึ้นเกิดจากสาเหตุใด ไม่เข้าใจประเภทของ Error
2. กลยุทธ์การดีบักเชิงวิทยาศาสตร์ (Debugging Strategies) ปฏิบัติตาม Scientific Debugging Cycle อย่างเคร่งครัด ใช้ Print Debugging, Assertions, และ Rubber Duck ได้อย่างเชี่ยวชาญ ใช้วิธีการตรวจสอบตัวแปรเป็นระยะและแก้ไขโค้ดได้อย่างมีแบบแผน ไม่สุ่มแก้ พยายามแก้โค้ดแบบสุ่มบางครั้ง (Trial & Error) แต่สามารถแก้ไขจุดผิดพลาดหลักได้ในที่สุด สุ่มแก้ไขโค้ดโดยไม่มีหลักการ ทำให้เกิดข้อผิดพลาดใหม่ซ้ำซ้อน
3. การออกแบบชุดกรณีทดสอบ (Test Case Design) ออกแบบ Test Cases ครบทั้ง 3 มิติ (Normal, Boundary, Invalid) และเขียนโค้ดตรวจสอบอัตโนมัติ (Automated Testing) ได้สมบูรณ์ ออกแบบ Test Cases ครอบคลุมทั้งกรณีปกติและกรณีขอบเขต แต่ยังขาดกรณีข้อมูลผิดปกติ (Invalid) ทดสอบเฉพาะกรณีข้อมูลปกติเพียงอย่างเดียว ไม่ได้ทดสอบกรณีขอบเขต (Boundary) ไม่มีการออกแบบชุดทดสอบ รันโปรแกรมครั้งเดียวแล้วด่วนสรุปว่าใช้งานได้
4. การส่งเสริม Growth Mindset ทางการศึกษา (Pedagogy & Mindset) ออกแบบกิจกรรมการเรียนรู้ที่ส่งเสริมให้นักเรียนมองเห็นคุณค่าของข้อผิดพลาด สร้างบรรยากาศที่เปิดกว้างและมีเจตคติที่ดีต่อการเขียนโค้ด สามารถอธิบายแนวทางการให้คำแนะนำแก่นักเรียนเมื่อนักเรียนพบข้อผิดพลาดในโค้ดได้ดี เข้าใจความสำคัญของ Growth Mindset แต่ยังขาดเทคนิคเชิงปฏิบัติในการนำไปใช้ในห้องเรียน มองว่าข้อผิดพลาดเป็นความล้มเหลว ขาดความอดทนในการตรวจสอบและแก้ไขโปรแกรม
เกณฑ์การตัดสินระดับคุณภาพ: คะแนนรวม 14 - 16 คะแนน = ระดับดีเยี่ยม (Excellent) | 11 - 13 คะแนน = ระดับดี (Good) | 8 - 10 คะแนน = ระดับพอใช้ (Fair) | ต่ำกว่า 8 คะแนน = ต้องได้รับการสอนเสริม (Needs Remediation)

ข้อสอบวัดสมรรถนะขั้นสูงเชิงการคิดคำนวณ (HOTS Assessment Bank)

แบบทดสอบวัดทักษะการคิดขั้นสูง (Higher-Order Thinking Skills: HOTS) ด้านการวิเคราะห์ข้อผิดพลาดเชิงตรรกะ (Analyzing) และการประเมินความถูกต้องของแบบจำลองวิทยาศาสตร์ (Evaluating) ตามแนวทาง สสวท.:

ข้อที่ 1 (ระดับการวิเคราะห์ - Analyzing):
นักเรียนเขียนโปรแกรม Scratch เพื่อจำลองการปล่อยลูกเหล็กทรงกลมให้ตกลงมาตามแนวดิ่งภายใต้แรงโน้มถ่วงของโลก ($g = 9.8\text{ m/s}^2$) โดยกำหนดสคริปต์การเคลื่อนที่ดังนี้: 
เมื่อคลิกธงเขียว
ตั้งค่า [velocity v] เป็น [0]
ตั้งค่า [y_pos v] เป็น [150]
วนซ้ำตลอด [
    เปลี่ยน [velocity v] ด้วย (-9.8)
    เปลี่ยน y ด้วย (velocity)
    ถ้า <(y_pos) < (-140)> แล้ว [
        ตั้งค่า [velocity v] เป็น [0]
    ]
]
เมื่อกดรันโปรแกรม พบว่า "ลูกเหล็กตกลงมาชนพื้นแล้ว แต่กลับจมทะลุพื้นเวทีหายไปด้านล่างอย่างต่อเนื่อง" ข้อใดวิเคราะห์สาเหตุของ Logic Error นี้ได้อย่างถูกต้องตามหลักการทำงานของคอมพิวเตอร์?
  • ก. เกิดจากค่าแรงโน้มถ่วง $g = -9.8$ เป็นค่าทศนิยมที่โปรแกรม Scratch ไม่รองรับ ต้องปัดเป็นจำนวนเต็ม $-10$
  • ข. บล็อกเงื่อนไขตรวจสอบค่าตัวแปร y_pos แต่คำสั่งเคลื่อนที่จริงกลับใช้ เปลี่ยน y ด้วย (velocity) โดยไม่ได้อัปเดตค่าของตัวแปร y_pos ให้ตรงกับตำแหน่ง y position ของตัวละครจริง ทำให้เงื่อนไข y_pos < -140 เป็นเท็จตลอดกาล
  • ค. เกิด Infinite Loop ที่ทำให้หน่วยความจำเต็ม จึงหยุดการเรนเดอร์ภาพกราฟิกบนหน้าจอ
  • ง. ในโปรแกรม Scratch ไม่สามารถตั้งค่าความเร็วติดลบได้ ค่าความเร็วจะกลายเป็นศูนย์โดยอัตโนมัติ
เฉลยข้อ ข. ถูกต้อง!
การวิเคราะห์เชิงลึก (Root Cause Analysis): นี่คือข้อผิดพลาดคลาสสิกที่พบบ่อยมากในหมู่นักเรียน:
  • ตัวแปร y_pos ถูกตั้งค่าเริ่มต้นไว้ที่ 150 แต่ภายในลูป forever กลับมีแต่คำสั่ง เปลี่ยน y ด้วย (velocity) ซึ่งสั่งย้ายพิกัดแกน Y ของสไปรต์จริงบนหน้าจอ แต่ ไม่มีคำสั่งอัปเดตตัวแปร ตั้งค่า y_pos เป็น (y position) เลย!
  • ส่งผลให้ตัวแปร y_pos ยังคงมีค่าคงที่เท่ากับ 150 เสมอ ไม่ว่าจะผ่านไปกี่วินาที
  • เมื่อตรวจสอบเงื่อนไข ถ้า <(y_pos) < (-140)> จึงได้ผลลัพธ์เป็น เท็จ (False: 150 ไม่น้อยกว่า -140) ทุกรอบการทำงาน คำสั่งรีเซ็ตความเร็วจึงไม่มีวันทำงาน ส่งผลให้ตัวละครตกลงไปเรื่อยๆ จนทะลุจอ
แนวทางแก้ไข: ต้องเปลี่ยนเงื่อนไขเป็น ถ้า <(y position) < (-140)> หรือใส่บล็อก ตั้งค่า y_pos เป็น (y position) ในลูป
ข้อที่ 2 (ระดับการประเมินค่า - Evaluating):
ในการสร้างแบบจำลองกฎของบอยล์ (Boyle's Law: $P_1V_1 = P_2V_2$ ที่อุณหภูมิคงที่) ครูให้นักเรียนเขียนฟังก์ชัน Python เพื่อหาความดันสุดท้าย $P_2 = \frac{P_1V_1}{V_2}$ นักเรียนส่งโค้ดต่อไปนี้มาตรวจ: 
def calculate_final_pressure(p1, v1, v2):
    try:
        p2 = (p1 * v1) / v2
        return p2
    except ZeroDivisionError:
        return 0.0
ในฐานะครูวิทยาศาสตร์ที่ประเมินความถูกต้องทางวิชาการและแนวคิดวิทยาการคำนวณ ข้อใดประเมินฟังก์ชันนี้ได้อย่างถูกต้องและสมบูรณ์ที่สุด?
  • ก. ฟังก์ชันนี้สมบูรณ์แบบแล้ว เพราะมีการใช้ try...except ป้องกันโปรแกรม Crash เมื่อ $V_2 = 0$
  • ข. ฟังก์ชันนี้มีข้อผิดพลาดร้ายแรงทางไวยากรณ์ (Syntax Error) เนื่องจากคำสั่ง return ในบล็อก except จะทำให้โปรแกรมหยุดทำงาน
  • ค. การส่งคืนค่า 0.0 เมื่อ $V_2 = 0$ ขัดแย้งกับหลักการทางฟิสิกส์อย่างรุนแรง เพราะเมื่อปริมาตรเข้าใกล้ศูนย์ ความดันต้องพุ่งเข้าสู่อนันต์ ($P \rightarrow \infty$) การคืนค่า 0.0 จะทำให้นักเรียนเข้าใจผิดว่าเมื่อบีบแก๊สจนหมดปริมาตรความดันจะหายไป ควรระงับและแจ้งเตือนข้อผิดพลาด (Raise Exception) หรือคืนค่าเตือนทางวิทยาศาสตร์
  • ง. ฟังก์ชันควรส่งคืนค่าติดลบ -1.0 เพื่อบ่งบอกว่าเกิดข้อผิดพลาดในการคำนวณ
เฉลยข้อ ค. ถูกต้อง!
การประเมินค่าเชิงบูรณาการวิทยาศาสตร์และวิทยาการคำนวณ:
  • ในมุมมองคอมพิวเตอร์ โปรแกรมนี้อาจดูเหมือนปลอดภัยเพราะไม่เกิด Crash (ไม่พ่น Exception ออกมา)
  • แต่ในมุมมอง ความถูกต้องของมโนทัศน์ทางวิทยาศาสตร์ (Scientific Conception) การคืนค่า 0.0 ถือเป็น Dangerous Fallacy เพราะตามกฎของบอยล์ $\lim_{V \to 0} \frac{k}{V} = \infty$ ความดันของแก๊สจะสูงเป็นอนันต์ ไม่ใช่กลายเป็นศูนย์
  • การดักจับข้อผิดพลาดแล้วแอบคืนค่า 0.0 เงียบๆ (Silent Error) จะสร้างความเข้าใจผิด (Misconception) ให้นักเรียนในชั้นเรียนวิทยาศาสตร์
แนวทางที่ถูกต้องตามหลักวิศวกรรมซอฟต์แวร์การศึกษา: ควรตรวจสอบ if v2 <= 0: raise ValueError("ปริมาตรของแก๊สต้องมากกว่าศูนย์เสมอตามกฎธรรมชาติ") เพื่อให้นักเรียนตระหนักว่าสภาวะดังกล่าวเป็นไปไม่ได้ในความเป็นจริง
